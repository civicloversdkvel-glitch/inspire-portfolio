# PART A — ZIP ANALYSIS

## A1. What the ZIP is
A **single-user, offline-first, mobile-style app** built in Google AI Studio: React 19 + TypeScript + Vite 6 + Tailwind CSS 4 + `motion` animations + `react-router-dom` 7 (`MemoryRouter` — no real URLs) + Capacitor 8 (Android wrapper with LocalNotifications). The whole UI is rendered inside a 400 px "phone simulator" frame with a scrolling 9-icon bottom navigation. **There is no backend, no login, no multi-user concept.** All data lives in the browser (`localStorage` keys `inspire_*`, plus one IndexedDB store `InspirePortfolioDB/portfolio_files`). The product purpose (from `metadata.json`): *"Offline student productivity and online earning tracking app."* Content theme: Pakistani students learning online-earning skills (messages/client outreach, orders, earnings, freelancing/account-selling/design/video/AI/dropshipping). Roman-Urdu text appears in learning content and reminders.

# PART B — TARGET PLATFORM

## 1. Purpose & scope
Build one integrated, responsive web platform for **The Inspire Business Academy** (Sadiqabad, Pakistan) combining: (1) public academy website and public student-project portfolio; (2) student registration → admin approval → permanent roll number → individual student portal; (3) Senior Admin and Junior Admin panels; (4) **every** productivity/learning feature of the supplied app, migrated from browser storage to Supabase (PostgreSQL, Auth, Storage, RLS).

## 2. Executive summary
The academy currently has a private, single-device student app with no accounts. The new platform lets the academy (a) market itself and showcase real student work publicly, (b) admit students through a controlled workflow with unique roll numbers, (c) track every student's daily activity, reports, targets, skills, learning and projects centrally, (d) moderate and publish student projects, and (e) run the academy with role-based admin tools, notifications, analytics and audit logs.

## 3. Product vision
*"Learn • Earn • Grow" — a trustworthy academy home where students build income-ready skills and a verified public portfolio, and the academy can see, guide and prove their progress."*

## 4. Business objectives & success metrics
| # | Objective | Metric / target (proposed SLO unless stated) |
|---|---|---|
| O1 | Professional public presence | Public site Lighthouse mobile ≥ 85 perf / ≥ 95 a11y & SEO; ≥ 1 inquiry or application per week after 60 days |
| O2 | Controlled admissions | 100 % of students have unique roll number; median application review time ≤ 48 h |
| O3 | Student engagement | ≥ 60 % of active students submit ≥ 4 daily logs/week; ≥ 70 % weekly-report submission |
| O4 | Showcase value | ≥ 3 published projects per active batch per month |
| O5 | Data safety | 0 cross-student data leaks (RLS tests green); backup restore test passes quarterly |
| O6 | Admin efficiency | Approve application ≤ 3 clicks; project moderation ≤ 2 min each |

## 5. Stakeholders & personas
| Persona | Description | Key needs |
|---|---|---|
| **Visitor / Parent** (Public) | Pakistani prospective student or parent on mobile data | Trust, clear courses, real student work, easy contact (WhatsApp/phone), apply |
| **Applicant** | Registered but not yet approved | Know status, fix corrections, no access to portal |
| **Student (e.g. Ayesha, 19)** | Learns skills, logs daily activity, builds portfolio on phone & laptop | Fast daily logging, streaks, reports, courses, games, upload work, feedback |
| **Junior Admin (instructor/mentor)** | Assists the owner | Review applications/reports/projects for assigned batches, assign tasks, announce |
| **Senior Admin (Owner — Adeel Bhatti)** | Runs the academy | Everything: approvals, roll numbers, roles, content, analytics, audit, backups |
| **System operator** | Whoever deploys (owner/ChatGPT) | Reproducible deployment, backups, monitoring |

## 6. User roles (summary — full matrix in §13)
`visitor (anon)` → `applicant` → `student` · `junior_admin` · `senior_admin`. Role stored only in `profiles.role` (server-controlled). Admin roles are never self-selectable.

## 7. Functional scope
In: all items in §9 requirements. Out: see §10.

## 8. Technology constraints (summary; detail in TRD)
React + TypeScript + Vite (SPA) · Supabase (Postgres, Auth, Storage, RLS, Edge Functions) · Hosting **Cloudflare (Workers & Pages) only** · AI via **Cloudflare AI Gateway** server-side · no Vercel · no secrets in frontend.

## 12. Business rules
| ID | Rule |
|---|---|
| BR-01 | A role is assigned only by server logic. A student can never approve themselves, pick a role, or edit `roll_number`, `batch`, `admission_date`, `account_status`. |
| BR-02 | Roll number: allocated once inside approval transaction; unique; permanent; never reused; corrections Senior-only, audited. |
| BR-03 | One application per account; duplicate email impossible; rejected applicant may reapply after cooldown (A-03). |
| BR-04 | Applicants cannot access student modules; students cannot access admin routes; Junior limited by permissions + batch scope; Senior has all. |
| BR-05 | **Active day** (streak) = messages ≥ 10 OR orders ≥ 1 OR portfolio improved OR topics read > 0 (configurable). Streak = consecutive active days ending today (or yesterday if today inactive yet), Asia/Karachi dates. Rewards: ≥30 "Pro Level"; ≥7 "Good Consistency"; ≥3 "On Fire"; else "Keep Going". |
| BR-06 | **Performance score** = round( min(1, messages/30)×40 + min(1, orders/2)×40 + min(1, streak/7)×20 ). Colour: ≥ 80 green, ≥ 50 yellow, else red. (Divisors use the effective daily targets.) |
| BR-07 | **Insights** (today): messages < target → "Increase outreach"; replies < 10 % of messages (if daily report exists) → "Improve message quality"; orders = 0 → "Focus on closing deals"; today's earnings > yesterday's → success; none triggered → "You are on track!". |
| BR-08 | **Weekly summary**: last 7 days; day score = orders×10 + messages; best/worst day; growth % = (this 7-day earnings − previous 7-day earnings)/previous ×100 (100 if previous = 0 and current > 0). |
| BR-09 | **Progress bar colour** (tasks): ≥100 % green, ≥50 % yellow, else red; (targets): ≥80 % green, ≥40 % yellow, else red. |
| BR-10 | **Reports**: daily = unique per student per date; weekly = per ISO week (Monday start); monthly = per calendar month; required text fields per form (Daily: problems, next-day plan; Weekly: weak point, next week goal; Monthly: biggest achievement, next-month target). Editable until `reviewed`; admin may `return`. Future-dated reports not allowed; late window: daily up to 7 days, weekly up to 14 days, monthly up to 10 days into next month. |
| BR-11 | **Course progress** % = completed lessons ÷ total lessons (published) in course; profile summary = completed ÷ total across all courses. **Learning guide progress** = read sections ÷ total sections. |
| BR-12 | **Game XP**: XP added = score of finished game (capped per game); level = floor(XP/100)+1; high score = max score per game. Server clamps scores (quiz ≤ 2000, puzzle ≤ 300, memory ≤ 300, shooter ≤ 5000, bubble ≤ 5000) to resist tampering. |
| BR-13 | **Portfolio**: Practice items are private forever (never reviewed/published). Showcase projects require ≥ 1 thumbnail image, title, summary, description, category before submission. |
| BR-14 | **Publication**: a project becomes public only if status = `published` set by an admin with `projects.publish`. Unpublish removes public copies. Student edits to a published project create a new revision requiring re-approval. |
| BR-15 | **Attribution**: student name shown publicly only if project `show_student_name` and student `public_profile_enabled`; client name hidden unless `show_client_name`. |
| BR-16 | Uploads limited by type/size (Backend Schema §8). SVG and executables rejected. |
| BR-17 | Chatbot: max 30 messages/student/day (configurable), 1000 chars/prompt, no storage of message text by default. |
| BR-18 | Every admin mutation of applications, roles, roll numbers, projects (approve/publish), settings, exports, deletions writes an audit record. |
| BR-19 | Suspended/withdrawn accounts lose access immediately (server-side); data retained per A-10. |
| BR-20 | Daily reminder sent at user's reminder time only if no daily log exists for today. |

## 14. User journeys (summary; screens in `03_App_Flow.md`)
J1 Visitor browses portfolio → opens project → clicks Apply. J2 Applicant registers → verifies email → fills application → receives "pending" → gets correction request → resubmits → approved with roll number → first login onboarding (skills). J3 Student daily loop: log activity → complete lessons → play a game → write daily report → see streak. J4 Student project: upload files → create project → submit → feedback → resubmit → approved → published → shared link. J5 Junior Admin reviews reports/projects for assigned batch and assigns a task. J6 Senior Admin approves application, grants a Junior permission, publishes project, reviews audit, exports monthly summary.

## 17. Edge cases
Duplicate signup email → Auth error "already registered", offer login/reset · applicant closes tab mid-form → draft autosave · email verification link expired → resend · approved while logged in → next refresh switches role (client refetches profile) · admin demotes last senior → blocked · student deletes file used as project thumbnail → block until replaced · upload interrupted → no `portfolio_files` row, orphan object queued for cleanup · project published then student withdraws → Senior can unpublish/anonymise · two admins review same project → optimistic version check (`updated_at`) · timezone change on device → business dates always Asia/Karachi · report for a week spanning two months → week belongs to its Monday's month for monthly totals? **No**: monthly totals use `daily_logs` by calendar month; weekly totals by ISO week · student with no skills selected hits Tasks → redirect to skills selection · AI service down → fallback to local snippets with notice · very large course lesson (> 50 KB) → paginate render.

## 21. Risks & mitigations (product-level; technical risks in TRD)
| Risk | Impact | Mitigation |
|---|---|---|
| Owner-supplied content/legal text missing (Privacy/Terms) | Launch blocker | Draft templates provided; owner approval step |
| Students lose enthusiasm because logging is slower than the offline app | Engagement ↓ | Autosave, optimistic UI, mobile-first Tasks screen |
| Low internet / data cost | Usability | Light pages, image optimisation, offline banner, retry |
| Public exposure of student work without consent | Reputation/legal | Explicit per-project consent, separate publish step, unpublish tool |
| Abuse of upload/AI quotas | Cost | Limits, rate limits, monitoring |
| Existing local data lost on device | Student frustration | Legacy import tool (FR-068) |
| AI Studio output diverges from schema | Rework | Exact names in `05`, Pass 2 compare, ChatGPT PR-based fixes |
